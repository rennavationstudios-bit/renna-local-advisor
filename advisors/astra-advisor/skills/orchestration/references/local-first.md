# Local-first auxiliary routing

Read the source kit's SETUP.md before enabling local workers. This reference
replaces the original author's machine-specific policy in the public export.

## Early local-contribution decision gate

### Allocate implementation before choosing root-only delivery

For substantial work, identify actual implementation and executable-test packets
as well as advisory work. Prefer qualified local builders/testers for suitable
bounded packets that replace primary work. Map each configured, qualified worker
to a useful packet or a concrete phase-specific skip reason in the existing
checkpoint. When two independent packets fit two available workers, dispatch them
concurrently with disjoint exact ownership. There is no minimum worker count or
utilization quota.

A scout checklist or design consultation does not settle implementation allocation.
Revisit deferred builder/tester packets when their design, interface or source
dependencies become ready, before implementing that work in the primary. Preserve
completed work; do not manufacture tasks or tests to occupy hardware. Tiny,
inherently sequential, restricted or unsuitable work stays in the primary. A real
capacity or guard failure is a valid fallback; hypothetical failure is not.

Select a compatible existing Advisor mode before dispatch. Under Sol, local
implementation uses delegate for non-substantial work or full for substantial
work; audit remains root implementation plus fresh review. Newly identified useful
independent implementation can justify a declared escalation from audit/solo before
dispatch. Local MCP workers use their own registry, admission and source-bound
receipt checks. Native role pins apply only to selected native agents, and full
with local implementers still requires fresh native Sol / High review.

The primary retains architecture, interfaces, integration, authoritative checks and
acceptance. Preserve source hashes, privacy, reservations and guarded on-demand
loading. Do not start or retune stopped resident services. Record delivered and
parent-verified useful work separately; status checks are not delegation.

Before selecting a cloud auxiliary or beginning substantial solo implementation,
identify an independent bounded contribution that could materially reduce primary
work. Consider local workers here, not only after deciding to delegate. Do not
reconsider on every short follow-up when scope and admission evidence are unchanged.

Prefer a suitable direct worker when its capability, exact source scope, current
admission and expected coordination/verification cost support that contribution.
Examples include an independent source map, test proposal, bounded implementation,
or first-pass review. Use inference-only for a supplied-source answer and tools only
for actual discovery/edit/test needs. Use Halo coordination when decomposition and
integration add value; an extra coordinator hop is not mandatory for direct GPU work.

Retain solo for trivial or inherently sequential work, already-covered work,
explicit no-local restrictions, or a capability mismatch. Inspect an existing
delivery before deciding whether a narrowly scoped repair is needed; do not resend
the whole assignment simply because it has not yet been accepted. Privacy rules
remain route-specific: private-only/no-cloud is not itself a prohibition on local
processing. Preserve exact source/privacy/ownership constraints.

Use current resource/admission evidence when dispatching. For a managed on-demand
worker, healthy:false with launchable:true can mean unloaded, not unavailable;
use its existing guarded worker route, which revalidates admission. Never apply
this exception to arbitrary stopped resident services. A busy reservation or failed
admission is a valid fallback reason. Do not repeatedly poll, start/stop/retune
resident models, or dispatch merely to meet a utilization quota.

For each substantial work phase, add one compact decision to its existing checkpoint:
local contribution and worker/receipt, or a concrete reason for solo/cloud
(no independent work, already covered, explicit restriction, live reservation,
unavailable capability, repeated request failure, or overhead exceeds useful work).
Separate invocation, delivery, complete/partial/blocked outcome, and parent-verified
use. Unknown history remains unknown; missing evidence is not a justified skip.
Do not create a new telemetry service or record raw prompts/secrets for this purpose.

The selected primary and effort, branded Advisor prerequisites and mode definitions,
source-hash checks and external-action authority are unchanged. Choose an existing
delegation mode if an auxiliary is selected; do not dispatch in a no-auxiliary solo
mode. Required fresh native acceptance review remains mandatory even when a local
first-pass review was useful. Expected savings never waive that review. This gate is
guidance, not measured savings or proof of historical avoidable skips.

## Dispatch and acceptance safeguards

Choose the execution contract from the deliverable:

- Read-only analysis from supplied sources: use inference, no allowedFiles,
  commands or tool services; put findings in the structured summary.
- Complete code-file proposals from a settled source/interface contract: use a
  builder role with inference and exact allowedFiles (including new files).
  Return code in the structured files array, not fenced code in the summary.
  allowedFiles authorizes isolated proposals; it does not edit the caller checkout.
- Repository discovery, iterative edits or executable tests: use tools with exact
  sourceFiles/allowedFiles and parent-selected checks as appropriate.

On BUILDER_OWNERSHIP_REQUIRED, add the missing exact allowedFiles and retry once.
Never relabel a coding request as a read-only tester/scout to pass validation.
A DELIVERED summary with no requested code is not a completed implementation.
Inspect returned files and hashes, integrate through the supported applier when
appropriate, and run authoritative tests. Sensitive-source read-only restrictions
remain unchanged; no code proposal may widen their scope.

Keep the selected Codex primary and effort authoritative. A local contribution is
an auxiliary proposal, not integration or acceptance authority. Preserve the
selected Advisor's native role contracts and fresh independent review requirements.
Report unmet model/effort prerequisites without changing the user's selection.

Choose useful independent bounded work: source mapping or first-pass review for
a scout; exact owned implementation or tests for a builder/tester. Prefer direct
assignments when possible. Use a local coordinator only when decomposition and
integration justify its extra work. No mandatory worker count or utilization goal.

Discover actual available tools and read private recipient config. The public
source snapshot's endpoint and path placeholders are not working configuration.
Observe current health/load, exact model identity, tool/context limits and shared
physical-device leases. Never start, stop, unload or retune another workload just
because a local worker is unavailable. Optional on-demand loading requires the
recipient's own qualified memory, application and ownership guards.

Use inference from an exact source capsule when it is sufficient. Use a bounded
tool loop only for necessary discovery, edits or tests. Give every writable job
exact disjoint file ownership and an isolated snapshot. Preserve original source
hashes and meaningful parent-owned checks. Run independent requests concurrently
only when resource ownership allows it; serialize shared-file and shared-device work.

Inspect completion as complete, partial or blocked, plus actual changed files,
source hashes and test evidence. Retain useful reviewed partial changes and request
one narrow repair when appropriate; never treat DELIVERED as accepted or repeat an
unknown write after a timeout. Cancellation requires confirmed cleanup before a
device reservation can be released.

Honor local-only/no-cloud, cloud-only/no-local and private-data rules. Keep keys in
protected local stores or inherited environment variables, never in worker prompts
or repository files. Allow fallback only within the user's selected mode; otherwise
return the precise blocker to the primary. Local review does not replace required
native acceptance review, and no local output authorizes publishing or deployment.
