# Local-first auxiliary routing

Read the source kit's SETUP.md before enabling local workers. This reference
replaces the original author's machine-specific policy in the public export.

Keep the selected Codex primary and effort authoritative. A local contribution is
an auxiliary proposal, not integration or acceptance authority. Preserve the
selected Advisor's native role contracts and fresh independent review requirements.
Report unmet model/effort prerequisites without changing the user's selection.

Choose useful independent bounded work: source mapping or first-pass review for
a scout; exact owned implementation or tests for a builder/tester. Prefer direct
assignments when possible. Use a local coordinator only when decomposition and
integration justify its extra work. No mandatory worker count or utilization goal.

Discover actual available tools and read private recipient config. The public
source snapshot's endpoint and path placeholders are not working configuration.
Observe current health/load, exact model identity, tool/context limits and shared
physical-device leases. Never start, stop, unload or retune another workload just
because a local worker is unavailable. Optional on-demand loading requires the
recipient's own qualified memory, application and ownership guards.

Use inference from an exact source capsule when it is sufficient. Use a bounded
tool loop only for necessary discovery, edits or tests. Give every writable job
exact disjoint file ownership and an isolated snapshot. Preserve original source
hashes and meaningful parent-owned checks. Run independent requests concurrently
only when resource ownership allows it; serialize shared-file and shared-device work.

Inspect completion as complete, partial or blocked, plus actual changed files,
source hashes and test evidence. Retain useful reviewed partial changes and request
one narrow repair when appropriate; never treat DELIVERED as accepted or repeat an
unknown write after a timeout. Cancellation requires confirmed cleanup before a
device reservation can be released.

Honor local-only/no-cloud, cloud-only/no-local and private-data rules. Keep keys in
protected local stores or inherited environment variables, never in worker prompts
or repository files. Allow fallback only within the user's selected mode; otherwise
return the precise blocker to the primary. Local review does not replace required
native acceptance review, and no local output authorizes publishing or deployment.
